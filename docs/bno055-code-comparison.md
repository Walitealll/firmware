# Изменения BNO055 относительно GitHub

Это снимок сравнения версии до добавления контроля полной калибровки. Соответствующий патч сохранен без изменений. Последующие изменения — проверка готовности перед выдачей кадров и выбор тактирования по результатам измерений — описаны в [bno055-absolute-ready.md](bno055-absolute-ready.md). В текущих исходниках internal использует внутренний генератор (`INT=0`), external — свой кварц (`EXT=1`).

Сравнение выполнено 5 ноября 2026 года для основной папки `C:/Users/Oleg/Desktop/project/frimware`. Через `git ls-remote` проверено: HEAD и main репозитория `https://github.com/Walitealll/firmware.git` указывают на `304dcb001e76954fcfdc3dde9981dd4a4ecc7baa`, тот же коммит, что и локальный HEAD. Сравнивались текущие локальные исходники с этим коммитом, не диагностическая прошивка и не копия `Desktop/firmware1`.

## Что изменилось

| Участок | GitHub | Текущая основная прошивка |
| --- | --- | --- |
| Сброс каждого BNO | В `FW_angle_init` вызывается только `fw_hw_bno_reset_release`: RESET устанавливается в 1. Программного сброса в этом пути нет. | `config_sensor` вызывает `reset_sensor`: CONFIG, 19 мс, запись `SYS_TRIGGER (0x3F) = 0x20`, пауза 700 мс, ожидание `CHIP_ID = 0xA0` и CONFIG, еще 50 мс перед настройкой. |
| Страница регистров | До прямых записей конфигурации страница явно не выбирается. | Перед настройкой/проверкой идентификатора устанавливается `PAGE_ID = 0`. |
| Источник тактирования | В обычной инициализации `SYS_TRIGGER` не записывается, CLK_SEL не проверяется. | В CONFIG записывается `SYS_TRIGGER = 0`, пауза 10 мс; проверяется CLK_SEL. Обе настройки `FW_BNO_USE_EXT_CRYSTAL_INT/EXT` равны 0 — явно выбран внутренний генератор. |
| Питание | Запись NORMAL. | Та же запись, затем пауза 10 мс и проверка чтением. |
| Выдержка после NDOF | `FW_BNO_OPR_SWITCH_MS = 7`. | `FW_BNO_OPR_SWITCH_MS = 600`. |
| Готовность fusion | Однократное раннее чтение режима; затем требуется хотя бы одна ненулевая компонента Euler; при статусе не 5 сразу ошибка. | После выдержки совместно читаются OPR_MODE, SYS_STATUS, SYS_ERR; ожидается статус 5 без ошибки при сохраненном NDOF; Euler может быть нулевым. При обнаруженном возврате в CONFIG разрешена одна повторная настройка без нового сброса. |
| Ошибка I2C в библиотеке | После ошибки следующие операции все еще выполняются; буфер вектора заранее не заполнен. При этом признак ошибки уже существовал, а `euler_store` уже проверял его. | После первой ошибки остальные операции до нового `bno055_select` блокируются; буферы обнуляются. Это защита от продолжения операции после сбоя, а не доказанная причина плавного дрейфа при успешном I2C. |

Важно: `CONFIG → NDOF` уже присутствовал на GitHub. Нельзя описывать изменение как добавление самого этого перехода. Существенное дополнение — настоящий сброс самого BNO и полная повторная настройка с ожиданием готовности.

Отпускание RESET не создает импульс сброса, если линия уже была высокой. Поэтому исходный путь не гарантировал свежий старт отдельно питаемого BNO после перезапуска STM32. Новый `RST_SYS` устраняет эту зависимость от прежнего состояния датчика. Это существенный кандидат для объяснения различий двух прошивок; отдельно от остальных изменений его влияние на дрейф на плате не измерялось.

## Что в расчете угла осталось прежним

- Оба датчика уже на GitHub использовали NDOF `0x0C`, а не режим без магнитометра. UNIT_SEL уже был `0x80`.
- `euler_store` по-прежнему выбирает нужную шину/адрес, вызывает `bno055_getVectorEuler()` и присваивает `heading_z = v.x`. Функция не изменена.
- `heading_diff_deg`, масштаб Euler и формула разности heading не изменены. Интегрирование угловой скорости, фильтр и вычитание дрейфа не добавлялись.
- Калибровка во время обычного опроса читалась и раньше. Новая прошивка не добавляет сохранение/восстановление профиля калибровки и не подменяет значения CALIB_STAT.

## Дополнительные изменения библиотеки

В `bno055.c` исправлены чтение одного байта OPR_MODE вместо частично заполненного enum, очистка CLK_SEL при отключении внешнего кварца, выбор CONFIG/page 0 в библиотечном reset и начальное обнуление буфера вектора. Но обычный путь запуска исходной основной программы не вызывал `bno055_setup`, `bno055_reset`, `bno055_getOperationMode` или `bno055_setExternalCrystalUse`. Поэтому исправления этих вспомогательных функций нельзя отдельно выдавать за установленную причину устранения исходного дрейфа.

## Что переносить в исходную прошивку

Подготовлен [bno055-working-vs-github.patch](bno055-working-vs-github.patch) — полный diff семи файлов BNO к коммиту `304dcb0`:

1. `App/FW_angle.c` — сброс, новая инициализация, ожидание готовности.
2. `config/fw_config.h` — регистры, параметры генератора, задержки и предел повторной настройки.
3. `App/FW_angle.h` — поля и коды результата инициализации, используемые новым кодом.
4. `Drivers/BNO055/bno055.c`.
5. `Drivers/BNO055/bno055_port.c`.
6. `Drivers/BNO055/bno055_port.h`.
7. `App/FW_init.c` — соответствующие диагностические сообщения; формулу угла не меняет.

В корне отдельной копии исходного проекта, если патч лежит по указанному абсолютному пути:

```powershell
git apply --check "C:/Users/Oleg/Desktop/project/frimware/docs/bno055-working-vs-github.patch"
git apply "C:/Users/Oleg/Desktop/project/frimware/docs/bno055-working-vs-github.patch"
```

Первую команду выполнить отдельно. Если она завершилась ошибкой, вторую не выполнять: копия отличается от проверенного исходника. К уже исправленной папке `frimware` этот патч повторно не применять.

Проверено на временной копии файлов коммита `304dcb0`: `git apply --check` проходит; после применения все семь файлов совпадают с текущими локальными исходниками с учетом окончаний строк. Патч включает весь проверенный набор изменений BNO; он не объявляется минимальным набором правок, каждая из которых необходима именно для устранения дрейфа.

Скрипты сборки, файлы CubeIDE и диагностическая программа в патч не включены. В текущем локальном `Core/Src/main.c` дополнительно есть второй подряд вызов `FW_sync_poll`; это отдельное изменение вне BNO, в патч оно не включено. Во время этого сравнения рабочие исходники и ELF не изменялись и не пересобирались.

## Что подтверждено на плате

Пользователь сообщил: исходная прошивка дает накопление heading internal, исправленная основная — нет. Ранее в исправленной основной прошивке после калибровки подтверждено отсутствие наблюдаемого накопления, оба датчика прошли инициализацию в NDOF без SYS_ERR. Это поддерживает результат всего набора исправлений, но не выделяет единственную причинную строку. Утверждение «дрейф убрала только калибровка» и утверждение «достаточно изменить только 7 на 600 мс» из этих данных не следуют.
