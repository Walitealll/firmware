# Сравнение полной прошивки с отдельной программой BNO055

Итог: пользователь подтвердил отсутствие накопления heading после калибровки
и в диагностической, и в основной программе. В основной программе оба BNO
успешно инициализировались, устройство перешло в ADVERTISING. После вращений
основной платы internal тоже достигает уровня калибровки 3. Подробный итог
и ограничения записаны в [bno055-heading.md](bno055-heading.md). Диагностическая
программа остается отдельным инструментом сравнения; рабочая программа —
`build/firmware.elf`, конфигурация `BNO055 firmware`.

Проверка нужна после полученных на неподвижных датчиках снимков: внешний gyro
менялся по осям до 5,1875°/с и оставался некалиброванным, а внутренний accel Z
во всех трех снимках был около −39,22 м/с². Это аномалии данных, которые нельзя
объяснить программным накопителем heading: снимки получены вызовами чтения
при остановленной основной программе. Успешный I2C сам по себе не доказывает
корректность всех принятых байтов или исправность датчиков.

Диагностическая программа использует те же SystemClock_Config, GPIO, I2C,
FW_angle_init и библиотеку BNO055, что и полная прошивка. Инициализация датчиков,
единицы и генератор BNO остаются одинаковыми. Она держит BLE в RESET и не
инициализирует UART, USB, ADC, SPI и прикладные таймеры. Это проверка влияния
остальных частей устройства, а не точная копия неизвестного рабочего примера
пользователя и не исправление дрейфа.

## Сборка

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-bno055-reference.ps1
```

Результат: `build/bno055-reference/firmware-bno055-reference.elf`, а также HEX и
BIN рядом. Обычный `build/firmware.elf` не перезаписывается. Вариант собирается
через `bno055-reference.mk`: только у объекта Core/Src/main.c переименован
прежний main, а вход программы берется из diagnostics/bno055_reference.c.
SystemClock_Config и Error_Handler повторно используются из того же Core/Src/main.c.

## Запуск в существующем CubeIDE

1. Завершить прежнюю Debug-сессию. Обновить проект Firmware через F5, чтобы IDE
   увидела общий файл `BNO055 reference.launch` в корне проекта.
2. Открыть Run → Debug Configurations, выбрать `BNO055 reference` и нажать Debug.
   Конфигурация создана на основе текущей рабочей firmware.elf_5.launch;
   ELF и загрузка символов указывают на абсолютный путь диагностического файла.
   На этой машине она использует существующий проект firmware.elf_5 и его
   настройки ST-Link/SWD. При удалении этого проекта потребуется выбрать
   существующий проект с настроенным STM32F103C8.
3. После остановки в main нажать Resume/F8 и оставить оба датчика неподвижными
   на устойчивой поверхности на 30 секунд. Временные breakpoints не должны
   прерывать этот интервал.
4. Остановить выполнение и выполнить в Debugger Console:

   ```text
   source C:/Users/Oleg/Desktop/project/frimware/scripts/bno055-reference-snapshot.gdb
   ```

5. Снова Resume, еще 60 секунд покоя, Suspend и та же команда. В этом файле
   читается память МК: повторение без Resume покажет тот же сохраненный снимок.

Успешная инициализация: `g_bno_reference_init_result=0`. Нужны оба вывода целиком.
Они включают heading и калибровку, а также `g_bno_reference_internal/external`:

- `gyro_dps`, `accel_ms2`: угловые скорости и ускорение через библиотеку;
- `sampled_ms`: время последнего диагностического опроса, обновляется раз в 500 мс;
- `io_ok`, `io_errors`: результат и счетчик ошибок чтений диагностического опроса;
- `gyro_id`: ожидается 0x0F; `self_test`: младшие четыре бита POST, 0x0F означает успех всех тестов;
- `calib_raw`: прямое чтение CALIB_STAT в том же опросе;
- `unit`: ожидается 0x80; младшая тетрада `opr_mode`: 0x0C;
- `pwr_mode`: 0; `sys_status`: 5; `sys_err`: 0; `sys_trigger`: выбранный генератор.

Если аномалии исчезнут, будем проверять различия активности периферии, BLE и
питания в полной программе. Если останутся, общими остаются плата, питание,
I2C/HAL и настройка BNO — это еще не доказывает аппаратную неисправность. Тогда
нужен контроль с известным рабочим примером и сравнение регистров/байтов.

Для возврата основной программы выбрать прежнюю конфигурацию Debug с
`build/firmware.elf` и снова загрузить ее.

## Полученный результат и проверка BLE без новой прошивки

Первая пара снимков диагностической программы: `init_result=0`, ошибок
диагностического I2C нет, оба чипа имеют GYRO_ID=0x0F, POST=0x0F, UNIT_SEL=0x80,
OPR_MODE=0x1C, PWR_MODE=0, SYS_STATUS=5, SYS_ERR=0. Внешний gyro достиг 3:
угловые скорости в двух снимках около `(-0.25,-0.4375,-0.3125)` и
`(0,0.1875,0.25)` °/с. Между снимками внешний heading изменился с 358,8125 до
359,125°, то есть на 0,3125°; разница sampled_ms равна 61,740 с. sampled_ms
останавливается вместе с МК, а BNO продолжает работать во время остановки:
эти метки нельзя использовать как точное прошедшее время для скорости дрейфа
между снимками с паузами Debug. Внешний mag остается 0, accel=1, sys=0.
Внутренний heading остался 2,9375°, gyro=3; его accel Z по-прежнему −39,22 м/с².

Различие с полной программой еще не устанавливает виновника: вместе с
активностью периферии изменились начальная калибровка, время работы и способ
снятия данных (периодический снимок вместо немедленного вызова из GDB).
Поэтому следующий тест сохраняет ту же диагностическую программу и состояние
BNO, меняя только RESET модуля BLE:

```text
source C:/Users/Oleg/Desktop/project/frimware/scripts/bno055-reference-ble-controls.gdb
bno-ble-release
```

Resume/F8, 60 секунд покоя, Suspend/interrupt, затем обычный reference snapshot.
После него `bno-ble-reset`, снова Resume/F8, 60 секунд покоя, Suspend/interrupt
и второй reference snapshot. При каждом снимке печатается фактический уровень
BLE nRESET: 0 — удерживается в сбросе, 1 — сброс отпущен. Команды используют
только PB14 из Core/Inc/main.h; RESET обоих BNO не затрагивается. Они не
инициализируют UART и не посылают AT-команды. Выход BLE в рекламный режим не
гарантируется: нужно отдельно отметить, появился ли модуль в поиске телефона.
Отсутствие изменения показаний при отпущенном RESET само по себе не исключит
влияние активной радиопередачи полной программы.

Файл команд загружен и проверен штатным ARM GDB по текущему ELF (типы GPIO,
HAL_GPIO_WritePin, значения GPIO_PIN_SET/RESET и защитная ветка до успешной
инициализации). Затем команды выполнены пользователем на устройстве. После
отпускания BLE RESET снимок показал GPIO=1, внешний heading=357,4375°,
gyro=3, mag=0, accel=1, sys=0, sampled_ms=293475; gyro_dps=(0,-0.4375,-0.25).
После возврата BLE в RESET: GPIO=0, heading=357,125°, те же уровни калибровки,
sampled_ms=355211; gyro_dps=(-0.25,-0.25,-0.4375). В обеих фазах I2C без
диагностических ошибок, нормальные режимы и POST=0x0F. Шум нескольких °/с и
потеря gyro=3 не воспроизвелись; heading меняется и с BLE в RESET. Наличие
реальной рекламы BLE пользователь не указал. Эта проверка не установила
причину дрейфа и не исключает влияние активной радиопередачи полной программы.

После этого пользователь подтвердил, что в той же сессии смог получить
gyro=3 и mag=3 одновременно. Следующий контроль — 2 минуты неподвижности с
наблюдением через Live Expressions, без Suspend между началом и концом,
с записью начального/конечного heading и всей калибровки. Нужно проверить,
остается ли mag=3 после укладки на поверхность, а не только при вращении.

Этот контроль выполнен: пользователь сообщил, что внешний heading не плывет,
а gyro и mag сохраняются на уровне 3. Таким образом, в диагностической
программе получено устойчивое состояние после калибровки. Это не подтверждает
пока ту же стабильность в полной программе: она проверяется следующим шагом.

## Возврат и проверка основной программы

Подготовлен отдельный файл `BNO055 firmware.launch`, который использует тот же
существующий проект CubeIDE и прежние настройки ST-Link, но загружает
`build/firmware.elf` и его символы. Этот основной ELF не пересобирался во время
диагностических опытов, его SHA256 остается
`6472389A3B61E8FC971E7E0E7CB9AEABDD8F0DFC6923545986751A1FAE574547`.

Завершить Debug, обновить проект Firmware через F5 и выбрать Run → Debug
Configurations → BNO055 firmware → Debug. После Resume/F8 нужно заново
выполнить калибровку: текущий FW_angle_init сбрасывает оба BNO, поэтому
достигнутые ранее gyro=3/mag=3 не сохранятся после нового запуска.

Если внешний gyro снова не достигает 3 за 30–60 секунд покоя, это отдельный
результат для сравнения с диагностической программой. Если gyro=3/mag=3
достигнуты, наблюдать оба heading две минуты в Live Expressions без Suspend,
записать начальные/конечные значения и уровни калибровки. После интервала можно
приостановить и снять сохраненные значения одной командой:

```text
source C:/Users/Oleg/Desktop/project/frimware/scripts/bno055-firmware-snapshot.gdb
```

Этот файл не вызывает функций на МК и не меняет режимы. Он печатает последние
сохраненные Euler/calib, результаты инициализации и диагностическую строку.
Результаты инициализации не являются непрерывным чтением регистров.

Проверка основной программы завершена пользователем: накопления угла нет,
external gyro=3/mag=3, оба init fail=0, NDOF/SYS_STATUS=5/SYS_ERR=0; в конце
зафиксирован `ADVERTISING FW_diagnostics OK OK`. Внутренний датчик сначала
имел mag=0 в сохраненном снимке, затем пользователь подтвердил достижение 3
при вращениях основной платы. Новые изменения расчетов heading после этого
контрольного прогона не вносились.
